# LinearPartition / LinearAlifold 高速化・追加検討（2026-09-19）

## 対象と変更

[前回の高速化](dafs_linfold_optimization_2026-09-19_ja.md)に加え、LinearNussinovで使われた残りの方法を `LinFold` の状態更新とプロファイル塩基対探索に適用できるか調べた。今回採用した変更は次の2点。

- inside 分配関数の `alpha` 更新で、同じ `unordered_map` 要素への2回のハッシュ検索を1回にした。状態の挿入順、走査順、`logsumexp` の計算順は変えていない。LinearPartition と LinearAlifold の両方に作用する。
- LinearAlifold の位置依存塩基対制約について、各左端・探索開始位置から次に使える右端を suffix 表に保持した。以前は `next_valid_pair` が不適格な候補を都度前方走査していた。配列長64～1024でだけ表を使い、最大約2 MiB。表は入力プロファイル・制約ごと、各 folding pass の開始時に作り直す。より長い入力では従来の探索に戻る。

候補判定の結果だけを再利用し、分配関数の加算順序と beam の同点優先順は維持した。

## 採用しなかった方法

- `unordered_map` の bucket 容量を各列の再計算で維持する方法は、初期BPP段階を予備測定で約2～3%短縮した。しかしRF00017-0の8条件中7条件でMCCが変わり、最大差は0.07138だった。状態の走査順が変わる影響が計算誤差の許容範囲を超えるため戻した。
- 各列の状態表を事前 `reserve` する方法も同じ入力の8条件すべてでMCCが変わり、最大差0.07138。十分な速度改善も確認できず戻した。
- LinearNussinovの generation stamp は候補集合の重複管理に使う。LinFoldの状態表はキーで重複を管理するため、同じ用途の置換にはならない。root cache、radix sort、最大 heap は、LinFoldでは既存の状態表、[前回導入した](dafs_linfold_optimization_2026-09-19_ja.md) `nth_element` による枝刈りと役割が重なる。状態表を compact vector に変える案は走査順の変更を伴い、上記 bucket 実験で精度への影響が確認されたため採用しなかった。

3入力×8条件の予備測定では、前回版の平均 wall が4.052秒だった。候補ごとの結果は以下のとおり。次候補表の予備版は単一ハッシュ検索も含む。

| 候補 | 予測一致 | 最大MCC差 | 平均 wall 秒 |
|---|---:|---:|---:|
| 単一ハッシュ検索 | 24/24 | 0 | 3.998 |
| bucket 容量再利用 | 17/24 | 0.07138 | 3.988 |
| 状態表の事前 `reserve` | 16/24 | 0.07138 | 4.018 |
| 単一ハッシュ検索＋次候補表（予備版） | 24/24 | 0 | 3.757 |

## 検証

比較対象は前回版 binary（SHA-256 `e7444644aae21b973a98d261d7defc47f73dbfa0193feb361a124883e5554070`）、今回版は `cd3e20c9d7267440bca9440e2d6b61748117dcdb0552e1398b180ff662654f19`。[設定](../benchmarks/configs/murlet-dataset1-linfold-optimization-iter100-beam100.json)のSHA-256は `23a935626952683d9c9bfc51fcd1241b7007a32a9af5189124251410833e581a`。ARM64、ViennaRNA 2.7.2、`OMP_NUM_THREADS=1`、8並列で測定した。

Murlet dataset1の85件について、LPC・LPVそれぞれ Alifold あり／なしの4条件を1回ずつ測った。各 binary 340 run。すべて `max-iter=100`、`align-beam=100`、`align-dd-beam=100`、`linfold-beam=100`、`fold-dd-beam=100`、`fold-final-beam=100`。両 binary の全runが成功し、metrics valid、品質評価完了。予測FASTA、品質値、時間項目を除いたDD trace・run summaryは **340/340件で完全一致**した。今回の採用変更には観測できる数値差もなかった。`ctest` は13/13通過。
